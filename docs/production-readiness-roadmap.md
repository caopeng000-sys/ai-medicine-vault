# AI Medicine Vault 上线补齐路线图

> 本文档用于指导项目从“本地可演示原型”补齐到“可上线运行产品”。后续开发应优先参考本文档拆分任务、设计实现和验收范围。

## 1. 当前状态

项目当前已经具备较完整的产品骨架：

- Next.js 前端工作台
- 成员、病历、药品、过敏记录等核心页面
- 本地 PostgreSQL + Prisma 数据层
- 药品图片上传、保存和预览
- 阿里百炼图片识别和 AI 助手意图路由
- 部分 API 测试、回归测试文档和构建验证流程

但当前状态仍更接近“本地开发版”和“产品验证版”。如果要真正上线，需要补齐身份、数据、安全、部署、监控、备份和合规等生产底座。

## 2. 上线目标

第一版上线目标不是做成大型医疗平台，而是做成一个稳定、可维护、数据安全的家庭健康资料管理工具。

上线后应满足：

- 用户只能访问自己的健康资料
- 数据可备份、可恢复、可迁移
- 图片和敏感资料存储安全
- AI 回答基于真实数据，并带来源依据
- 核心链路有测试和回归保障
- 服务异常能被发现、定位和恢复
- 页面和接口具备基本生产稳定性

## 3. 优先级分层

### P0：上线前必须补齐

P0 是上线门槛。未完成 P0，不建议对外开放。

### P1：上线前强烈建议补齐

P1 不一定阻塞小范围试用，但会直接影响稳定性、可维护性和后续扩展。

### P2：上线后持续优化

P2 可以作为产品成熟度提升项，不阻塞第一版上线。

## 4. P0 必须补齐项

### 4.1 账号体系与数据隔离

**目标**

让每个用户只能看到、创建、修改和删除自己的数据。

**当前进展**

已完成 Auth.js 登录接入（GitHub OAuth、session、`middleware` 路由保护、登录页）。repository 层继续通过 `RepositoryContext` 按用户过滤。开发环境仍保留 `user-development` 回退；生产环境必须登录。

**当前问题**

历史文档描述的问题已解决。后续需在生产环境配置 `AUTH_SECRET`、GitHub OAuth 与托管 PostgreSQL，并执行 `npm run prisma:deploy`。

**开发任务**

- 接入认证方案，例如 NextAuth/Auth.js、Clerk 或自建邮箱登录
- 新增 `User` 数据模型
- 将 `Member`、`MedicalRecord`、`Medicine`、`AllergyRecord` 等业务数据关联到用户
- 所有列表、详情、创建、编辑、删除接口都必须按当前用户过滤
- 未登录访问业务页面时跳转登录页
- API 层统一校验用户身份

**验收标准**

- 未登录用户不能访问业务数据
- 用户 A 不能通过 URL 或 API 访问用户 B 的数据
- 创建数据时自动绑定当前用户
- 删除、编辑接口只能操作当前用户拥有的数据

### 4.2 生产数据库与迁移策略

**目标**

将本地 PostgreSQL 迁移为可上线使用的托管数据库，并建立稳定迁移流程。

**当前进展**

- 迁移文件已纳入版本控制（含 Auth.js 模型）
- 新增 `npm run prisma:deploy` 用于生产部署
- 详见 [production-database-setup.md](./production-database-setup.md)

**当前问题**

本地 PostgreSQL 适合开发，但不能作为线上生产数据库。线上需要高可用、备份、权限控制和迁移流程。

**开发任务**

- 选择托管 PostgreSQL，例如 Supabase、Neon、Railway、Render 或云厂商 RDS
- 配置生产 `DATABASE_URL`
- 区分本地、测试、生产环境变量
- 使用 Prisma migration 管理 schema 变更
- 禁止直接在生产库手工改表
- 增加迁移前备份流程

**验收标准**

- 生产环境可稳定连接数据库
- `prisma migrate deploy` 可在生产环境执行
- 本地和生产环境配置互不污染
- 迁移失败时有回滚或恢复方案

### 4.3 图片存储迁移到对象存储

**目标**

将药品图片从数据库二进制存储迁移到对象存储，数据库只保存图片元数据和访问地址。

**当前问题**

当前图片保存在 PostgreSQL 字节字段中，小规模可用，但长期会增加数据库体积、备份成本和查询压力。

**开发任务**

- 选择对象存储，例如 S3、Cloudflare R2、阿里云 OSS、Supabase Storage
- 新增图片上传服务
- 药品表保存 `imageUrl`、`imageKey`、`imageMimeType`、`imageName`
- 为私有图片生成受控访问 URL
- 限制图片大小和类型
- 为旧数据设计迁移脚本

**验收标准**

- 新上传图片进入对象存储
- 药品卡片能正常显示图片
- 未授权用户不能访问他人图片
- 超过大小或非法类型的图片会被拒绝

### 4.4 API 安全与输入校验

**目标**

保证所有写入和敏感接口都有统一的身份校验、参数校验和错误处理。

**当前进展**

- 统一 API 错误响应（401/404/400/500）via `api-errors.ts`
- 写接口与 AI 接口使用 Zod 校验；助手问题/搜索词长度限制 500/200 字
- 图片上传校验 MIME 类型与 8MB 上限
- AI 调用结构化日志（用户、路由、耗时、成功/失败）

**当前问题**

部分历史 API 仍待逐步迁移到统一 helper；分布式限流与 AI 意图级日志仍可加强。

**开发任务**

- 所有 API 必须校验登录态
- 所有写接口必须使用 Zod schema 校验请求体
- 文件上传接口校验文件大小、MIME 类型和扩展名
- AI 接口校验输入长度和空值
- 统一错误响应格式
- 防止前端传入任意 `memberId` 操作他人数据

**验收标准**

- 非法请求返回明确错误
- 未登录请求返回 401
- 越权请求返回 403 或 404
- API 不暴露内部堆栈和敏感信息

### 4.5 AI 调用保护与成本控制

**目标**

防止 AI 接口被滥用，避免费用失控，同时保证回答不越过医疗边界。

**当前问题**

当前已经接入阿里百炼，但还需要限流、调用记录和更清晰的错误兜底。助手查询与图片识别接口已加入基础内存限流（单实例有效）。

**开发任务**

- 为 `/api/assistant/query` 和药品图片识别接口增加频率限制
- 记录 AI 调用日志：用户、意图、耗时、成功/失败、模型名称（基础 JSON 日志已接入）
- 限制单次输入长度和图片大小
- 对不支持的问题返回固定兜底提示
- AI 回答必须基于查询结果，不允许自由医疗建议
- 增加 AI 调用失败时的非 AI 兜底结果

**验收标准**

- 高频调用会被限制
- AI 服务不可用时页面不崩溃
- 回答中保留来源依据
- 不输出诊断、治疗、替代用药建议

### 4.6 备份与恢复

**目标**

确保用户健康资料和图片可以恢复。

**当前问题**

健康资料属于高价值数据，一旦丢失会严重影响用户信任。

**开发任务**

- 配置数据库自动备份
- 配置对象存储备份或版本控制
- 制定恢复流程
- 定期做恢复演练
- 提供用户数据导出能力的基础设计

**验收标准**

- 能从最近备份恢复数据库
- 能恢复药品图片
- 有明确恢复步骤文档
- 至少完成一次恢复演练

## 5. P1 强烈建议补齐项

### 5.1 部署流水线

**目标**

让构建、测试、部署变成可重复流程。

**开发任务**

- 配置 Vercel 或其他部署平台
- 配置 GitHub Actions
- PR 或 main 分支推送时自动运行：
  - `npm run build`
  - 现有 tsx 测试
  - Prisma schema 校验
- 生产部署前检查环境变量

**验收标准**

- 构建失败不会部署
- 测试失败不会部署
- 生产环境变量缺失时部署失败并提示原因

### 5.2 可观测性与错误监控

**目标**

上线后能发现问题、定位问题、追踪问题。

**开发任务**

- 接入错误监控，例如 Sentry
- 记录 API 请求错误
- 记录 AI 调用失败
- 记录数据库异常
- 为关键接口增加耗时日志

**验收标准**

- 页面运行时异常能进入监控平台
- API 500 能被记录
- AI 调用失败能看到原因和时间

### 5.3 回归测试体系

**目标**

保障药品管理、成员管理、AI 助手等主链路不被后续改动破坏。

**开发任务**

- 将现有手工回归文档转成可执行 E2E 测试
- 覆盖：
  - 新增药品
  - 上传药品图片
  - AI 图片识别回填
  - 编辑药品
  - 删除药品
  - 药品搜索和分类筛选
  - AI 助手药品问答
- 增加测试数据初始化脚本

**验收标准**

- 本地可一键执行主流程测试
- CI 可运行核心测试
- 测试失败能定位到具体场景

### 5.4 数据导出

**目标**

让用户可以导出自己的健康资料，便于就医和备份。

**开发任务**

- 支持导出成员健康摘要
- 支持导出药品清单
- 支持导出病历记录
- 第一版可先支持 JSON 或 CSV
- 后续扩展 PDF 就医摘要

**验收标准**

- 用户只能导出自己的数据
- 导出内容结构清晰
- 导出过程不包含他人数据

### 5.5 隐私政策与免责声明

**目标**

明确产品边界、数据使用方式和医疗风险提示。

**开发任务**

- 新增隐私政策页面
- 新增医疗免责声明页面
- 在 AI 助手和药品识别处展示简短风险提示
- 说明 AI 仅做资料整理，不替代医生或药师判断

**验收标准**

- 用户能在页面访问隐私政策和免责声明
- AI 相关页面有明确边界提示
- 文案不暗示诊断或治疗能力

## 6. P2 后续优化项

### 6.1 药品批次管理

**目标**

支持同一种药存在多盒、多批次、不同有效期的情况。

**开发任务**

- 新增 `MedicineBatch` 或 `StockLot` 模型
- 每个批次记录数量、有效期、购买时间、图片
- 主药品记录展示聚合库存和最近过期批次

### 6.2 AI 问答能力扩展

**目标**

在安全边界内支持更多资料问答。

**可扩展意图**

- 查找退烧药、止痛药、感冒药等药品
- 查询某成员最近一次就医记录
- 查询某成员过敏史
- 生成就医前摘要
- 根据药品库和病历生成待咨询医生的问题清单

### 6.3 多成员协作

**目标**

支持家庭成员之间共享和协作维护健康资料。

**开发任务**

- 家庭空间模型
- 成员邀请
- 权限角色
- 只读和可编辑权限

## 7. 推荐开发顺序

### 第一阶段：上线门槛

1. 账号体系与数据隔离
2. API 鉴权和输入校验
3. 生产数据库
4. 图片对象存储
5. AI 限流和调用日志
6. 备份恢复方案

### 第二阶段：稳定运行

1. 部署流水线
2. 错误监控
3. 回归测试体系
4. 数据导出
5. 隐私政策和免责声明

### 第三阶段：产品增强

1. 药品批次管理
2. 更多 AI 意图
3. 就医摘要导出
4. 家庭协作

## 8. 开发执行原则

后续根据本文档开发时，应遵循：

- 每次只推进一个明确主题
- 每个主题先写设计文档，再写实施计划
- 涉及数据结构变更时必须包含迁移说明
- 涉及用户数据时必须先考虑权限边界
- 涉及 AI 时必须保留来源依据和兜底提示
- 涉及上传时必须限制大小、类型和访问权限
- 完成后至少运行构建和相关测试
- 未经明确要求，不自动提交或推送远程

## 9. 第一批建议拆分任务

建议下一步优先拆分为以下开发任务：

1. `用户登录与数据隔离`
2. `API 鉴权与统一错误响应`
3. `图片对象存储迁移`
4. `AI 调用限流与日志`
5. `生产数据库部署方案`
6. `备份与恢复文档`

其中最优先的是 `用户登录与数据隔离`。这是所有生产能力的入口，也是后续云数据库、对象存储、AI 限流和导出能力的基础。
