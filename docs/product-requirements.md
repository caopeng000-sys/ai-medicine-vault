# AI Medicine Vault 产品需求文档（PRD）

## 1. 文档说明

本文档基于飞书文档《个人健康记录管理平台产品需求文档（PRD）》整理，并结合当前项目 `AI Medicine Vault` 的实际工程状态进行收敛。

当前项目定位不是“AI 医生”，而是一个面向个人和家庭的健康资料管理平台。AI 能力应优先服务于信息检索、资料摘要和就医沟通准备，避免直接给出诊断、治疗或替代用药建议。

## 2. 项目背景

个人健康信息通常分散在不同载体中，例如医院病历、检查报告截图、处方单、药盒说明、家庭成员提醒、聊天记录和个人记忆。用户真正需要复诊、买药或咨询医生时，往往很难快速找到关键上下文。

典型问题包括：

- 家里现在有哪些常备药？
- 药品是否过期，是否仍然适合继续保留？
- 某个症状以前是否出现过？
- 上一次就诊医生给了什么建议？
- 之前使用某种药后是否出现过不适？
- 用户或家庭成员是否存在明确过敏史？
- 当前问题就医前，应该整理哪些资料和问题？

AI Medicine Vault 希望通过结构化记录和 AI 辅助检索，帮助用户更好地管理个人健康资料，并在就医前形成更清晰的沟通材料。

## 3. 产品定位

AI Medicine Vault 是一个个人健康记录与家庭药品管理平台。

核心价值：

- 集中保存病历、药品、过敏史和健康笔记。
- 帮助用户按人、时间、症状、药品维度回顾健康资料。
- 在用户提问时，基于个人历史记录生成可核对的摘要。
- 在就医或咨询药师前，整理问题清单和资料清单。
- 通过明确的医疗安全边界，降低 AI 输出误导风险。

## 4. 目标用户

### 4.1 个人健康管理用户

关注自己病历、体检、用药和过敏记录的人群。

### 4.2 慢病或长期用药用户

需要长期维护复诊记录、处方药、用药时间和身体反应。

### 4.3 家庭健康管理者

为老人、儿童或家庭成员记录常备药、就诊记录和过敏信息的人。

### 4.4 就医前准备用户

希望在问诊前快速整理症状变化、历史资料、已用药品和待咨询问题。

## 5. 产品目标

### 5.1 业务目标

- 建立一个结构化的个人健康资料库。
- 支持用户管理病历、药品、过敏史和健康事件。
- 支持家庭成员维度的数据组织。
- 引入 AI 辅助用户查询历史记录、生成摘要和准备就医问题。
- 为后续数据可视化、文件识别、药品提醒等能力打基础。

### 5.2 用户目标

- 快速知道自己或家人有哪些健康记录。
- 快速查找某次就诊、某种药品、某类症状相关信息。
- 在就医前整理“已发生什么、用过什么、想问什么”。
- 减少忘记病史、忘记药名、忘记过敏信息的情况。

### 5.3 安全目标

- 不直接提供医学诊断。
- 不直接推荐处方药或替代药。
- 不让 AI 输出替代医生或药师判断。
- 所有 AI 结果都必须体现“仅供整理和沟通参考”的边界。

## 6. MVP 范围

第一阶段 MVP 应聚焦“记录、查看、检索、整理”，暂不做高风险医疗决策功能。

### 6.1 MVP 必做功能

#### 6.1.1 成员管理

- 支持创建个人档案。
- 支持维护基础信息：姓名、关系、出生年份、备注。
- 支持记录过敏史摘要。

#### 6.1.2 病历记录

- 支持手动新增病历记录。
- 字段包括：就诊日期、医院或地点、科室、症状描述、诊断结果、医生建议、备注。
- 支持按成员和时间筛选。

#### 6.1.3 药品记录

- 支持手动新增家庭药品。
- 字段包括：药品名称、规格、数量、有效期、存放位置、适用成员、备注。
- 支持查看即将过期和已过期药品。

#### 6.1.4 过敏记录

- 支持维护过敏原、反应描述、严重程度、发现时间、备注。
- 在成员详情页展示醒目的过敏信息。

#### 6.1.5 AI 资料问答

- 用户可以基于个人资料提问。
- AI 回答必须引用或说明其依据的历史记录。
- 支持问题示例：
  - “我上次感冒是什么时候？”
  - “家里有哪些退烧药？”
  - “我之前对哪些药有过不适？”
  - “下次看医生前我应该整理哪些问题？”

#### 6.1.6 就医准备清单

- 根据用户选择的病历、症状和用药记录，生成就医前资料清单。
- 输出内容包括：症状摘要、历史记录摘要、已用药品、过敏提示、待咨询问题。

### 6.2 MVP 暂不做功能

- 不做诊断结论。
- 不做处方药推荐。
- 不做药品替代方案推荐。
- 不做自动判断“是否需要就医”。
- 不做复杂医疗合规认证。
- 不做医院系统对接。
- 不做真实医生或药师在线咨询。

## 7. 功能需求

### 7.1 用户与成员模块

用户可以创建多个家庭成员档案，并将病历、药品和过敏记录关联到具体成员。

核心字段：

- 成员 ID
- 姓名或昵称
- 关系
- 出生年份
- 性别，可选
- 过敏摘要
- 备注

验收标准：

- 用户可以新增、编辑、查看成员。
- 用户可以在成员详情中查看关联病历、药品和过敏记录。
- 删除成员前需要明确提示关联数据影响。

### 7.2 病历管理模块

用于记录每次就诊或重要健康事件。

核心字段：

- 病历 ID
- 成员 ID
- 就诊日期
- 医院或地点
- 科室
- 症状描述
- 诊断结果
- 医生建议
- 处方或用药说明
- 附件，后续扩展
- 备注

验收标准：

- 用户可以新增、编辑、查看病历。
- 病历列表支持按成员、时间倒序展示。
- 病历详情应清楚展示症状、诊断、建议和用药信息。

### 7.3 药品管理模块

用于管理家中常备药和历史用药。

核心字段：

- 药品 ID
- 药品名称
- 规格
- 数量
- 有效期
- 存放位置
- 适用成员
- 用途备注
- 禁忌或注意事项备注

验收标准：

- 用户可以新增、编辑、查看药品。
- 药品列表展示有效期状态。
- 即将过期和已过期药品需要有明显标记。
- 平台只提示过期状态，不直接建议替代药品。

### 7.4 过敏记录模块

用于记录明确或疑似过敏事件。

核心字段：

- 过敏记录 ID
- 成员 ID
- 过敏原
- 反应描述
- 严重程度
- 发现日期
- 备注

验收标准：

- 用户可以新增、编辑、查看过敏记录。
- 成员详情页需要突出显示过敏信息。
- AI 回答涉及用药历史时，应优先提示相关过敏记录。

### 7.5 AI 问答模块

AI 问答用于“查找和整理用户已有资料”，不用于直接医疗判断。

能力范围：

- 检索用户历史病历。
- 检索家庭药品记录。
- 检索过敏记录。
- 生成就医沟通摘要。
- 生成待确认问题清单。

输出要求：

- 说明回答基于哪些记录。
- 对不确定内容明确标注“不确定”。
- 对医疗相关建议统一提示“请咨询医生或药师确认”。
- 不生成诊断结论。
- 不直接推荐药品替代方案。

验收标准：

- 用户提问后能获得结构化回答。
- 回答中包含资料来源或依据说明。
- 高风险问题触发安全提示。

### 7.6 就医准备模块

用于把分散记录整理成就医前可阅读材料。

输出结构：

- 当前问题摘要。
- 相关历史病历。
- 近期用药记录。
- 过敏史提示。
- 建议向医生或药师确认的问题。

验收标准：

- 用户可以选择成员和相关记录生成清单。
- 输出内容清晰、可复制、可导出，导出能力可后续实现。
- 输出不得给出诊断或治疗结论。

## 8. 页面规划

### 8.1 首页 / 仪表盘

展示整体健康资料概览：

- 成员列表
- 最近病历
- 即将过期药品
- 过敏提醒
- AI 问答入口
- 就医准备入口

### 8.2 成员详情页

展示某个成员的完整健康资料：

- 基础信息
- 过敏信息
- 最近病历
- 关联药品
- 就医准备入口

### 8.3 病历列表与详情页

支持查看、筛选、新增和编辑病历。

### 8.4 药品管理页

支持查看家庭药品、有效期状态、存放位置和备注。

### 8.5 AI 问答页

提供围绕个人资料的问答体验，并展示回答依据。

### 8.6 就医准备页

引导用户选择成员、症状和相关记录，生成结构化就医清单。

## 10. 技术方案建议

### 10.1 当前前端技术栈

- Next.js 16
- React 19
- TypeScript
- Tailwind CSS v4
- shadcn/ui
- Radix UI
- Lucide React

### 10.2 后续后端建议

- 使用 Next.js API Routes 或 Server Actions 承载轻量业务接口。
- 使用 PostgreSQL 作为主数据库。
- 使用 Prisma 管理数据模型和迁移。
- 使用对象存储保存用户上传附件。
- AI 检索可先从结构化字段检索开始，再逐步引入向量数据库。

### 10.3 AI 方案建议

第一阶段不急于引入复杂向量数据库。建议路线：

1. 先实现结构化数据录入和查询。
2. 再实现基于数据库记录的 AI 摘要。
3. 当附件、病历文本和长文档数量变多后，再引入向量检索。

AI 输出需要统一经过安全提示和边界模板。

## 11. 安全与合规要求

健康数据属于高敏感个人信息，产品设计应默认保护隐私。

基础要求：

- 所有用户数据必须隔离。
- 敏感数据传输必须使用 HTTPS。
- 数据库存储需要考虑加密策略。
- 访问接口需要鉴权。
- 日志中不得记录完整病历、药品、过敏等敏感内容。
- AI 提示词和响应记录需要避免泄露其他用户数据。
- 导出和删除数据需要明确用户确认。

医疗安全要求：

- 不提供诊断。
- 不替代医生或药师。
- 不直接推荐处方药。
- 不直接推荐替代药物。
- 对药物冲突、过敏等内容只做“风险提示”和“请专业人员确认”。

## 12. 里程碑规划

### 阶段一：产品基础与信息架构

目标：

- 完成 PRD 和页面信息架构。
- 明确 MVP 范围。
- 完成前端基础布局和设计系统。

产出：

- PRD 文档。
- 页面结构草图。
- 基础首页和导航框架。

### 阶段二：核心记录能力

目标：

- 实现成员管理。
- 实现病历记录。
- 实现药品管理。
- 实现过敏记录。

产出：

- 可录入和查看的基础健康资料库。

### 阶段三：AI 辅助整理

目标：

- 实现基于个人资料的 AI 问答。
- 实现就医准备清单。
- 加入安全边界和输出模板。

产出：

- 可基于历史资料回答问题和生成就医清单的 AI 辅助能力。

### 阶段四：可视化与体验优化

目标：

- 完善仪表盘。
- 增加筛选和时间线。
- 优化移动端体验。
- 增加导出能力。

产出：

- 更完整的个人健康资料工作台。

## 13. 风险与挑战

### 13.1 数据隐私风险

健康数据敏感度高，需要从早期就建立权限、加密、日志脱敏和删除机制。

### 13.2 AI 误导风险

AI 可能生成不准确或过度自信的健康建议，因此必须限制输出边界，并将产品定位为资料整理工具。

### 13.3 数据录入成本

用户手动录入病历和药品可能比较麻烦，后续需要考虑拍照识别、文件上传和模板化录入。

### 13.4 家庭成员权限边界

家庭场景下，不同成员之间的数据访问权限需要谨慎设计。

## 14. 成功指标

MVP 阶段可以关注：

- 用户是否能在 3 分钟内完成第一条病历记录。
- 用户是否能快速添加家庭常备药。
- 用户是否能在成员详情页看清病历、药品和过敏信息。
- AI 回答是否能明确引用已有记录。
- 就医准备清单是否能被用户直接复制使用。

## 15. 待确认问题

- 是否优先支持单用户，还是一开始就支持家庭成员？
- 是否需要账户登录，还是先做本地原型？
- 第一阶段是否需要数据库，还是先用本地模拟数据验证页面和流程？
- 是否需要支持病历附件上传？
- AI 能力第一版接入真实模型，还是先用模拟响应验证交互？
- 移动端是否作为第一优先级？

## 16. 结论

AI Medicine Vault 的第一阶段应避免过早进入复杂医疗判断，而是先建立可靠的个人健康资料库。产品的核心价值不是替代医生，而是帮助用户把分散资料整理清楚，并在就医或咨询药师前形成结构化上下文。

下一步建议先实现成员、病历、药品、过敏四个基础模块，再逐步加入 AI 问答和就医准备清单。
