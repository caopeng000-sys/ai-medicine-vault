# 药品图片识别与 AI 回填设计文档

## 背景

当前药品录入流程主要依赖手工填写，字段包括药品名称、分类、剂量、规格、有效期和使用说明。对于家庭药箱场景，用户往往已经有药盒或说明书照片，更希望通过拍照或上传图片快速完成录入。

本次能力目标是在现有 `新增药品记录` 弹窗中增加“本地上传图片 -> AI 识别 -> 自动回填表单 -> 用户确认后保存”的流程，减少重复录入成本，同时保留人工确认，以降低医疗相关误识别风险。

## 目标

- 支持用户在 `新增药品记录` 弹窗内上传本地图片。
- 服务端调用阿里百炼视觉模型识别药盒或说明书内容。
- 自动回填以下表单字段：
  - `name`
  - `category`
  - `dosage`
  - `specification`
  - `instructions`
  - `purpose`
- 返回一段 AI 摘要，说明识别依据和不确定项。
- 用户可修改回填结果，确认后再保存药品记录。

## 非目标

- 第一版不做手机拍照入口。
- 第一版不做多张图片联合识别。
- 第一版不自动创建药品记录，必须由用户确认保存。
- 第一版不做药物相互作用分析或诊断建议。
- 第一版不把原始图片写入数据库。

## 用户流程

1. 用户打开 `新增药品记录` 弹窗。
2. 用户选择本地图片文件。
3. 用户点击“AI 识别图片”。
4. 前端将图片以 `multipart/form-data` 提交到新接口 `POST /api/medicines/extract`。
5. 服务端读取图片，转为百炼兼容接口可接受的输入格式，请求视觉模型。
6. 模型返回结构化 JSON：
   - 药品名称
   - 分类
   - 剂量
   - 规格
   - 使用说明
   - 治疗疾病/适应症
   - AI 摘要
   - 低置信度提醒
7. 前端将结果回填到表单。
8. 用户检查并修改后，点击“保存药品”，沿用现有 `POST /api/medicines` 写入数据库。

## 方案选型

### 方案 A：服务端直连阿里百炼视觉模型

推荐采用该方案。

优点：

- API Key 保留在服务端，不暴露到浏览器。
- 结构化输出和错误处理可以集中在服务端做。
- 便于后续切换模型或新增 OCR/多图策略。

缺点：

- 需要新增一个图片识别接口和服务端解析逻辑。

### 方案 B：前端直连百炼 API

不采用。

原因：

- API Key 会暴露。
- 难以统一处理格式化输出和错误提示。

### 方案 C：先 OCR，再做二次总结

暂不采用。

原因：

- 第一版范围过大。
- 会引入更多失败节点和调试成本。

## 技术设计

### 模型与接口

- 提供商：阿里百炼 DashScope OpenAI 兼容接口
- Base URL：`https://dashscope.aliyuncs.com/compatible-mode/v1`
- 推荐模型：
  - 默认使用 `qwen-vl-plus`
  - 若后续需要加强说明书 OCR，可升级为 `qwen-vl-ocr`

### 环境变量

新增本地环境变量：

```env
DASHSCOPE_API_KEY=你的阿里百炼密钥
```

该变量只写入本地 `.env` 或 `.env.local`，不提交到仓库。

### 新增服务端模块

建议新增：

- `lib/ai/dashscope.ts`
  - 封装百炼调用
- `features/medicine-vault/medicine-image-extractor.ts`
  - 封装提示词、结果解析、字段清洗
- `app/api/medicines/extract/route.ts`
  - 接收图片，调用提取器，返回结构化结果

### 返回结构

接口返回统一 JSON：

```json
{
  "message": "图片识别完成。",
  "data": {
    "name": "布洛芬缓释胶囊",
    "category": "止痛退烧",
    "dosage": "0.3g/粒",
    "specification": "0.3g*20粒",
    "instructions": "口服，按说明书或医嘱使用。",
    "purpose": "用于缓解发热和轻中度疼痛。",
    "aiSummary": "从药盒正面识别到药名、规格和适应症信息；用法用量信息较模糊，建议人工确认。",
    "warnings": [
      "有效期未可靠识别，请手动填写。",
      "使用说明存在低置信度，请以说明书为准。"
    ]
  }
}
```

## Prompt 设计

要求模型：

- 只根据图片内容提取，不得虚构。
- 以结构化 JSON 返回结果。
- 识别不清时返回空字符串，不乱猜。
- `category` 使用项目已有语言风格，如：
  - 抗感染
  - 止痛退烧
  - 抗过敏
  - 感冒对症
  - 营养补充
  - 设备耗材
- `purpose` 要写成用户看得懂的“治疗疾病/适应症”。
- `instructions` 要尽量短，优先提取说明书或包装上的原始用法。
- 额外输出 `aiSummary` 和 `warnings`。

## 前端设计

在现有 `新增药品记录` 弹窗中新增：

- 图片上传区域
- “AI 识别图片”按钮
- 识别中状态
- 识别摘要区
- 低置信度提醒区

表单字段调整：

- 保留现有字段
- 新增 `purpose`
- `category` 后续可升级为下拉，但第一版保持文本输入并支持 AI 回填

交互规则：

- 未上传图片时，“AI 识别图片”按钮禁用。
- AI 成功后自动回填，但不自动提交。
- AI 失败时提示用户手动填写，不阻塞录入。

## 错误处理

需要覆盖以下情况：

- 未配置 `DASHSCOPE_API_KEY`
- 上传文件为空
- 文件不是图片
- 文件过大
- 百炼接口超时
- 模型未返回有效 JSON

错误策略：

- 接口统一返回中文错误信息
- 前端弹窗显示错误提示
- 不影响用户手动录入药品

## 安全与医疗边界

- AI 仅做图片内容提取与摘要，不做诊断和治疗建议。
- 若图片内容无法确认，明确提示“请以药盒或说明书原文为准”。
- 不生成替代用药推荐。
- 不根据图片推断超出包装/说明书的用法。

## 测试策略

需要验证：

1. 正常图片上传后能返回结构化字段。
2. 回填后仍可手动修改。
3. 保存后药品记录正常写入数据库。
4. 缺少 API Key 时能给出明确错误。
5. 非图片文件上传时有明确提示。
6. 模型返回异常时不会导致整个录入弹窗失效。

## 分阶段实现

### 第一阶段

- 新增百炼服务端封装
- 新增图片识别接口
- 新增药品录入弹窗中的图片上传和 AI 回填
- 新增 `purpose` 字段

### 第二阶段

- 优化分类标准化映射
- 支持多图识别
- 支持说明书 OCR 强化模式

## 实施建议

先完成第一阶段最小闭环：

- 本地上传单张图片
- 百炼识别
- 结构化回填
- 人工确认保存

这一版完成后，药品录入就会从“纯手填”升级成“AI 辅助录入”，而且不会把风险推给用户。
