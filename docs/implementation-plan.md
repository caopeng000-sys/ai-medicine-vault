# AI Medicine Vault 开发实施计划

## 1. 计划说明

本文档用于把当前已有资料转成可执行开发计划。

已有资料：

- `docs/product-requirements.md`：产品需求文档。
- `docs/system-architecture.md`：系统架构设计文档。
- `docs/visual-designs/`：早期视觉概念稿。
- `docs/frontend-playbook.md`：前端开发规范。

当前策略：

- 第一阶段先做前端可点击原型。
- 使用本地 mock 数据验证信息架构和交互流程。
- 暂不接数据库、认证和真实 AI 模型。
- 医疗相关 AI 能力先收敛为资料摘要和就医问题清单。
- 每个阶段完成后先本地验证，只有用户明确要求时再提交到 GitHub。

## 2. MVP 范围确认

第一版 MVP 聚焦“记录、查看、检索、整理”四件事。

### 2.1 MVP 包含

- 首页 / 健康仪表盘。
- 成员管理。
- 病历记录。
- 药品管理。
- 过敏记录。
- 就医准备清单。
- AI 问答入口和模拟响应。

### 2.2 MVP 不包含

- 真实用户登录。
- 真实数据库持久化。
- 文件上传。
- OCR。
- 向量数据库。
- 真实 AI 模型调用。
- 医生端。
- 管理后台。
- 医学诊断。
- 药品替代推荐。
- 处方药推荐。

## 3. 技术实施原则

- 使用 Next.js App Router。
- 默认使用 TypeScript。
- 页面优先使用 Server Components。
- 需要交互状态的局部组件使用 Client Components。
- UI 优先使用 shadcn/ui 基础组件组合。
- 图标使用 Lucide React。
- 样式使用 Tailwind CSS v4 语义 token。
- mock 数据放在 `features/<domain>/`。
- 复杂页面组件放在 `components/<domain>/`。
- 先保证桌面端体验，再兼顾移动端响应式。

## 4. 阶段规划

## 阶段一：应用信息架构与全局布局

目标：建立产品骨架，让应用从单页概念页变成可扩展的工作台结构。

### 任务

- 设计应用级导航结构。
- 增加左侧导航或顶部导航。
- 建立页面容器、标题区、操作区、内容区的统一布局。
- 定义主要路由：
  - `/`
  - `/members`
  - `/records`
  - `/medicines`
  - `/allergies`
  - `/visit-prep`
  - `/assistant`
- 抽取布局组件，例如 `AppShell`、`PageHeader`。
- 将首页从纯营销感页面调整为产品工作台入口。

### 验收标准

- 用户能从首页进入各个模块。
- 页面结构清晰，导航可用。
- 桌面和移动端没有明显溢出或重叠。
- `npm run build` 通过。

## 阶段二：mock 数据与领域模型

目标：在不接数据库的情况下，先建立稳定的数据形状。

### 任务

- 在 `features/medicine-vault/` 下建立 mock 数据。
- 定义 TypeScript 类型：
  - `Member`
  - `MedicalRecord`
  - `Medicine`
  - `AllergyRecord`
  - `VisitPreparation`
- 准备 2 到 3 个家庭成员样例。
- 准备病历、药品、过敏、健康事件样例。
- 增加基础查询 helper，例如按成员筛选、按日期排序、计算药品过期状态。

### 验收标准

- mock 数据能支撑所有页面展示。
- 类型定义清晰，不使用 `any`。
- 后续切换数据库时，数据字段能自然映射到 Prisma schema。
- `npm run build` 通过。

## 阶段三：成员管理前端原型

目标：实现成员列表和成员详情，建立后续所有健康记录的入口。

### 页面

- `/members`
- `/members/[id]`，可先用静态 mock 路由或列表内详情面板替代。

### 任务

- 成员列表卡片。
- 成员基础信息展示。
- 过敏摘要高亮。
- 最近病历摘要。
- 当前药品摘要。
- 从成员详情跳转病历、药品、过敏模块。

### 验收标准

- 用户可以看到所有成员。
- 用户可以查看某个成员的健康资料概览。
- 过敏信息足够醒目。
- `npm run build` 通过。

## 阶段四：病历记录模块

目标：实现病历列表和详情展示。

### 页面

- `/records`

### 任务

- 病历列表。
- 按成员筛选。
- 按时间倒序展示。
- 病历详情抽屉或详情面板。
- 症状、诊断、医生建议、处方备注分区展示。
- 新增病历按钮先做静态入口或弹窗原型。

### 验收标准

- 用户能按成员查看病历。
- 病历信息层级清楚。
- 不把诊断字段做成 AI 判断结果。
- `npm run build` 通过。

## 阶段五：药品管理模块

目标：实现家庭药品库页面。

### 页面

- `/medicines`

### 任务

- 药品列表。
- 药品状态标记：
  - 正常
  - 即将过期
  - 已过期
- 按成员或用途筛选。
- 展示规格、数量、有效期、存放位置、注意事项。
- 新增药品按钮先做静态入口或弹窗原型。

### 验收标准

- 用户能快速看到家中药品。
- 过期状态清晰。
- 页面不推荐替代药品。
- `npm run build` 通过。

## 阶段六：过敏记录模块

目标：建立过敏信息的独立管理页面，并在其他模块中突出显示。

### 页面

- `/allergies`

### 任务

- 过敏记录列表。
- 按成员筛选。
- 严重程度标记。
- 反应描述展示。
- 与成员详情联动展示。

### 验收标准

- 用户能快速看到每个成员的过敏风险。
- 严重过敏醒目展示。
- AI 相关页面能引用过敏记录。
- `npm run build` 通过。

## 阶段七：就医准备清单

目标：把已有 mock 数据整理成就医前可复制内容。

### 页面

- `/visit-prep`

### 任务

- 选择成员。
- 展示相关病历、药品、过敏记录。
- 生成静态或模拟的就医准备摘要。
- 输出结构：
  - 当前问题摘要
  - 相关历史记录
  - 近期用药
  - 过敏提示
  - 建议咨询医生或药师的问题
- 增加复制按钮，第一版可以只做 UI，不必真正写入剪贴板。

### 验收标准

- 输出内容可直接用于就医前整理。
- 不提供诊断和治疗建议。
- 医疗免责声明可见。
- `npm run build` 通过。

## 阶段八：AI 助手模拟页

目标：先验证 AI 问答的产品体验，不接真实模型。

### 页面

- `/assistant`

### 任务

- 问答输入框。
- 推荐问题列表。
- 模拟回答区域。
- 回答中展示依据记录。
- 固定安全提示。
- 支持切换不同推荐问题的 mock 响应。

### 验收标准

- 用户能理解 AI 的定位是资料整理助手。
- 回答必须有来源依据。
- 页面明确提示不替代医生或药师。
- `npm run build` 通过。

## 阶段九：数据库与持久化

目标：在前端流程稳定后，引入真实数据层。

### 任务

- 引入 Prisma。
- 选择 PostgreSQL 服务。
- 建立 Prisma schema。
- 迁移 mock 数据字段到数据库模型。
- 实现成员、病历、药品、过敏基础 CRUD。
- 根据需要选择 Server Actions 或 Route Handlers。

### 验收标准

- 数据刷新后仍然保留。
- 基础 CRUD 可用。
- 所有查询按用户隔离预留 `userId`。
- `npm run build` 通过。

## 阶段十：真实 AI 接入

目标：在已有资料库基础上接入受控 AI 能力。

### 任务

- 选择 AI Provider。
- 设计 Prompt 模板。
- 设计安全输出模板。
- 实现基于记录的上下文构造。
- 实现回答来源引用。
- 增加高风险问题拒答或收敛回答策略。

### 验收标准

- AI 只基于用户资料做整理和摘要。
- 不输出诊断、治疗、替代药建议。
- 回答包含资料来源。
- 高风险问题有安全提示。
- `npm run build` 通过。

## 5. 推荐开发顺序

短期推荐执行顺序：

1. 阶段一：应用信息架构与全局布局。
2. 阶段二：mock 数据与领域模型。
3. 阶段三：成员管理前端原型。
4. 阶段四：病历记录模块。
5. 阶段五：药品管理模块。
6. 阶段六：过敏记录模块。
7. 阶段七：就医准备清单。
8. 阶段八：AI 助手模拟页。

完成这些后，再进入数据库和真实 AI。

## 6. 第一轮开发建议

下一次正式开发建议先做：

- `AppShell` 全局布局。
- 页面导航。
- mock 数据类型定义。
- 首页改造成产品工作台。

建议第一轮完成后，用户就能看到一个“像产品”的可点击骨架。

## 7. 验证要求

每轮开发至少执行：

```bash
npm run build
```

涉及页面和交互时，还需要：

- 启动本地开发服务。
- 在浏览器检查桌面视图。
- 在窄屏宽度检查移动端布局。
- 确认没有明显文字溢出、按钮错位和内容遮挡。

## 8. Git 规则

- 默认不自动提交。
- 只有用户明确要求“提交”“推送”“上传 GitHub”时才执行 Git 提交或推送。
- 提交信息统一使用中文。
