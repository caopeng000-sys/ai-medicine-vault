# AI Medicine Vault 系统架构设计文档

## 1. 文档说明

本文档基于飞书文档《系统架构设计图》整理，并结合当前项目 `AI Medicine Vault` 的技术栈和产品边界重新设计。

原始架构文档提出了前端 UI、后端 API、数据库和 AI 服务四层结构。本文档保留这个整体方向，但对数据库选型、AI 能力边界、MVP 实施顺序和医疗安全要求做了收敛。

## 2. 架构目标

系统架构需要满足以下目标：

- 支持个人和家庭成员维度的健康资料管理。
- 支持病历、药品、过敏史、健康事件等结构化数据存储。
- 支持基于个人资料的 AI 检索、摘要和就医准备。
- 保持前端工程简单、清晰、可演进。
- 在早期 MVP 阶段避免过度拆分服务。
- 从设计上限制 AI 医疗风险，不提供诊断、治疗或替代用药建议。
- 为后续文件上传、OCR、向量检索和权限体系预留空间。

## 3. 总体架构

## 4. 分层设计

### 4.1 用户界面层

职责：

- 展示健康资料、家庭成员、药品、过敏记录和就医准备内容。
- 提供新增、编辑、筛选、查询等交互入口。
- 承载 AI 问答和就医准备清单的用户体验。
- 通过 Server Components 优先渲染页面，减少不必要的客户端状态。

当前技术：

- Next.js 16
- React 19
- TypeScript
- Tailwind CSS v4
- shadcn/ui
- Radix UI
- Lucide React

设计原则：

- 路由文件保持轻量。
- 复杂 UI 放在 `components/<domain>/`。
- 领域数据和业务逻辑放在 `features/<domain>/`。
- 默认使用 Server Components。
- 只有表单交互、弹窗状态、实时输入、浏览器 API 等场景才使用 Client Components。

### 4.2 应用服务层

职责：

- 处理页面提交、API 请求和业务流程。
- 执行权限校验。
- 调用数据访问层读写数据库。
- 调用 AI 编排层生成摘要和问答结果。
- 统一处理错误、审计和安全边界。

建议实现：

- MVP 阶段使用 Next.js Route Handlers 或 Server Actions。
- 不急于拆分独立后端服务。
- 当 AI 任务、文件处理或异步任务变复杂时，再拆分后台任务队列或独立服务。

典型服务：

- `memberService`
- `medicalRecordService`
- `medicineService`
- `allergyService`
- `aiSummaryService`
- `visitPreparationService`

### 4.3 数据访问层

职责：

- 隔离业务代码与数据库实现。
- 统一封装查询、写入、分页、筛选和事务。
- 避免页面组件直接操作 ORM。

建议实现：

- 使用 Prisma 作为 ORM。
- 使用 PostgreSQL 作为主数据库。
- Repository 或 Service 内部封装常用查询。

数据库选择说明：

- 飞书原文建议 MySQL。
- 当前项目建议优先使用 PostgreSQL。
- PostgreSQL 更适合后续 JSON 字段、全文检索、复杂查询和 pgvector 扩展。

### 4.4 AI 编排层

职责：

- 将用户问题转换为可控的检索和摘要任务。
- 从数据库中选择相关病历、药品、过敏记录。
- 组织 Prompt 和上下文。
- 调用 AI 模型。
- 对 AI 输出进行安全边界处理。
- 返回带来源依据的结构化结果。

MVP 阶段能力：

- 历史资料检索。
- 记录摘要。
- 就医前问题清单生成。
- 过敏和已用药提示。

MVP 阶段不做：

- 诊断结论。
- 治疗方案。
- 处方药推荐。
- 替代药推荐。
- 自动判断是否需要就医。

后续扩展：

- 文件 OCR 后的病历内容检索。
- 长文档向量化。
- 多轮健康资料问答。
- 个人健康时间线总结。

## 5. 核心模块架构

### 5.1 成员模块

用于管理个人或家庭成员档案。

主要能力：

- 创建成员。
- 编辑基础信息。
- 查看成员详情。
- 汇总成员关联的病历、药品和过敏记录。

关联数据：

- `Member`
- `MedicalRecord`
- `Medicine`
- `AllergyRecord`

### 5.2 病历模块

用于管理就诊记录和重要健康事件。

主要能力：

- 新增病历。
- 编辑病历。
- 按成员和时间查看病历。
- 在 AI 问答和就医准备中作为重要上下文。

### 5.3 药品模块

用于管理家庭药品和历史用药。

主要能力：

- 新增药品。
- 维护规格、数量、有效期、存放位置。
- 标记即将过期和已过期药品。
- 在 AI 问答中作为资料来源。

安全边界：

- 只提示药品信息和过期状态。
- 不直接建议替代药品。
- 不判断是否应继续服药。

### 5.4 过敏模块

用于管理明确或疑似过敏记录。

主要能力：

- 记录过敏原。
- 记录反应描述。
- 记录严重程度。
- 在成员详情和 AI 输出中优先提示。

### 5.5 AI 问答模块

用于帮助用户查询和整理已有健康资料。

典型问题：

- “我上次感冒是什么时候？”
- “家里有哪些退烧药？”
- “我以前对哪些药不舒服？”
- “下次看医生前我应该准备哪些问题？”

回答结构：

- 简短结论。
- 相关记录依据。
- 不确定信息提示。
- 建议向医生或药师确认的问题。

### 5.6 就医准备模块

用于将分散资料整理成就医前可用清单。

输出内容：

- 当前问题摘要。
- 相关历史病历。
- 近期用药记录。
- 过敏史提示。
- 待咨询医生或药师的问题。

## 7. 关键数据流

### 7.1 查看健康记录

```text
用户打开页面
  → Next.js Server Component 请求数据
  → 应用服务层校验用户身份
  → 数据访问层查询 PostgreSQL
  → 页面渲染成员、病历、药品和过敏信息
```

### 7.2 新增病历

```text
用户提交病历表单
  → Server Action 或 Route Handler 接收请求
  → 校验字段和用户权限
  → 写入 MedicalRecord
  → 返回成功状态
  → 页面刷新或局部更新
```

### 7.3 AI 问答

```text
用户输入问题
  → 应用服务层识别问题类型
  → 查询相关成员、病历、药品、过敏记录
  → 构造受控 Prompt
  → 调用 AI 模型
  → 安全边界检查
  → 返回结构化回答和资料来源
```

### 7.4 就医准备清单

```text
用户选择成员和相关记录
  → 查询历史病历、药品、过敏记录
  → AI 生成摘要和待确认问题
  → 应用服务层追加免责声明
  → 前端展示可复制清单
```

## 8. AI 安全边界

AI 输出必须遵守以下规则：

- 不输出诊断结论。
- 不输出治疗方案。
- 不推荐处方药。
- 不推荐替代药。
- 不判断是否需要立即就医。
- 对药物冲突和过敏内容只做风险提示。
- 明确建议用户咨询医生或药师确认。
- 回答必须说明依据来自哪些历史记录。
- 没有记录依据时必须说明资料不足。

建议统一输出结构：

```text
摘要：
基于记录的依据：
需要确认的问题：
风险提示：
免责声明：
```

## 9. 认证与权限设计

MVP 阶段可以先使用单用户或模拟用户，正式版本需要完整认证。

后续建议：

- 使用 NextAuth.js 或等价认证方案。
- 支持邮箱登录或第三方登录。
- 所有业务数据都必须绑定 `userId`。
- 服务层必须校验当前用户是否有权访问目标数据。
- 家庭成员数据默认只属于当前用户。

暂缓设计：

- 医生角色。
- 管理员角色。
- 多用户共享同一家庭空间。

这些能力可以在核心资料管理稳定后再设计。

## 10. 数据安全与隐私

健康数据属于敏感个人信息，需要从早期建立保护边界。

基础要求：

- HTTPS 传输。
- 数据库访问鉴权。
- 用户数据按 `userId` 隔离。
- 日志不得记录完整病历、过敏、处方内容。
- AI 请求上下文只包含当前用户授权的数据。
- 删除、导出、分享等操作需要明确确认。
- 后续附件存储需要私有 bucket 或带签名 URL。

加密建议：

- 密码不自行存储，交给认证服务或成熟方案处理。
- 对特别敏感字段预留字段级加密能力。
- 生产环境密钥统一使用环境变量或密钥管理服务。

## 11. 部署架构

MVP 推荐部署方式：

```text
Vercel
  ├─ Next.js 前端页面
  ├─ Route Handlers / Server Actions
  └─ 环境变量配置

PostgreSQL
  └─ Supabase / Neon / RDS

Object Storage
  └─ 后续用于病历附件和报告图片

AI Provider
  └─ OpenAI / Claude / 其他兼容模型
```

早期不建议：

- 过早拆分微服务。
- 过早引入复杂消息队列。
- 过早引入独立向量数据库。
- 过早设计医生端和运营后台。

## 12. 演进路线

### 阶段一：前端信息架构

- 完成首页。
- 完成基础导航。
- 完成成员、病历、药品、过敏的页面结构。
- 使用模拟数据验证流程。

### 阶段二：数据持久化

- 引入 PostgreSQL。
- 引入 Prisma。
- 建立核心数据模型。
- 完成基础 CRUD。

### 阶段三：AI 辅助整理

- 实现 AI 问答。
- 实现资料来源引用。
- 实现就医准备清单。
- 加入安全输出模板。

### 阶段四：文件与检索增强

- 支持附件上传。
- 支持 OCR 文本提取。
- 引入全文检索。
- 根据数据规模评估是否引入向量检索。

### 阶段五：家庭协作与权限

- 支持家庭空间。
- 支持成员共享。
- 支持更细粒度权限。

## 13. 当前仓库落地建议

结合当前项目状态，下一步建议优先做：

1. 建立应用导航和基础布局。
2. 新增成员管理页面。
3. 新增病历、药品、过敏三个模块的列表页和表单。
4. 先用本地模拟数据串通核心流程。
5. 再引入数据库和认证。
6. 最后接入 AI 问答和就医准备清单。

这样可以先验证产品体验，再逐步提高技术复杂度。

## 14. 待确认问题

- MVP 是否先做单用户本地原型？
- 是否优先做移动端体验？
- 数据库使用 Supabase、Neon 还是自建 PostgreSQL？
- 认证是否采用 NextAuth.js？
- 是否需要从第一版开始支持附件上传？
- AI 模型优先使用哪一家服务？
- 是否需要在页面中加入更明显的医疗免责声明？

## 15. 总结

AI Medicine Vault 的架构应保持“前端体验清晰、后端边界明确、数据安全优先、AI 能力受控”的方向。

短期内，系统不需要复杂微服务架构。使用 Next.js 全栈能力、PostgreSQL、Prisma 和受控 AI 编排，就足以支撑 MVP。等真实数据、附件和 AI 检索需求增长后，再逐步引入对象存储、OCR、全文检索和向量检索。
